## Names, plainly

| Name | Mac | What it is |
|---|---|---|
| `pig` | both | Shell script. Runs `gb grok-pi`. |
| `gb` | both | Launcher script. Starts the fork pager with an ACP agent command. |
| `grok-pi` | both | Launcher name inside `gb`. Means "Pi, through the fork". |
| `grok-fork` | both | The fork pager (the TUI). `~/.grok/bin/grok-fork`. |
| `grok-pi-acp` | both | Stdio ACP host for Pi. `~/.grok/bin/grok-pi-acp`. |
| `~/.local/bin/grok-pi` | both | Different program: Dwsy's standalone `@dwsy/grok-pi`, 74 MB. `pig` no longer runs it. |

## What `pig` runs (Mini, verified)

1. `~/.local/bin/pig` → `~/.grok-hub/scripts/hub/pig` (symlink). Line 4: `exec .../gb grok-pi "$@"`.
2. `gb` (`~/.grok-hub/scripts/hub/gb`): `CMD[grok-pi]="${GROK_PI_ACP_BIN:-grok-pi-acp}"`, where `GROK_PI_ACP_BIN` is `~/.grok/bin/grok-pi-acp` (gb:72-84). `PAGER_BIN` is `~/.grok/bin/grok-fork` (gb:~10-16).
3. Final exec (gb:467): `env -u PAGER GROK_RESUME_CMD="grok grok-pi" ~/.grok/bin/grok-fork --agent-cmd ~/.grok/bin/grok-pi-acp`.
4. `grok-pi-acp` (`crates/codegen/xai-grok-pager-bin/src/bin/grok-pi-acp.rs`):
   - `pi_version::ensure_compatible_pi_host("pi")` (line ~96-101). Min Pi `0.99.0` (`grok_pi/pi_version.rs:23`).
   - Writes bridge extensions to temp files and passes them as `--extension` (lines ~140-330).
   - `PiRpc::spawn` runs `pi` with `--mode rpc` plus the extension flags (line ~470).
   - `PiBootstrap::load` with a 60 s timeout (line ~487).
   - Serves ACP on stdout to the pager.
5. `pi` on the Mini: `~/.local/bin/pi` → `~/.pi/agent/bin/pi`, a launcher that execs `~/.pi/agent/install/releases/$(cat current-version)/node_modules/.bin/pi`. Current version `1.5.0`. `pi --version` prints `1.5.0`.

Full chain: `pig` → `gb` → `grok-fork` (pager, TUI) → `grok-pi-acp` (ACP host) → `pi --mode rpc` (Pi core and extensions) → `cliproxy` provider (from `~/.pi/agent/settings.json`: `defaultProvider: cliproxy`, `defaultModel: gemini-3.8-flash-high`).

## Failures on sab-air, ranked by how basic

Sab's screenshot (`/private/tmp/claude-501/.../images/2.png`) shows a Pi session in the fork pager: cwd `~/.pi`, chat area holding only status lines, slash menu open, footer `gemini-3.8-flash-high · cliproxy (none) · always-approve`. Terminal title `pi`.

1. **Chat is flooded with status lines (verified source, cause partly guessed).**
   - Symptom: `Usage cleanup started`, `Usage cleanup completed`, `daily-memory: session note dropped`, `Running shortcut shift+up`, `Running shortcut shift+down` ×2 in the chat, no answers.
   - `Running shortcut ${key}` comes from `extensions/pi-grok-shortcut-manager/dispatch.ts:24` (`ctx.ui.notify`). Each shortcut press fires a notify.
   - `daily-memory: session note dropped` comes from `~/.pi/agent/extensions/daily-memory-nudge.ts:20` (outside the repo; `ctx.ui.notify`).
   - `Usage cleanup …` was not found in the repo or `~/.pi/agent/extensions` (grep). Source unknown.
   - Guess: `notify` renders as chat lines in the remote-TUI path. Not verified on sab-air.
   - Fix (guess): make the shortcut notify quiet or status-line only (`dispatch.ts:24`); move or drop the daily-memory notify (`daily-memory-nudge.ts:20`); find the usage-cleanup emitter.

2. **`pi` on PATH is a different Pi on sab-air (verified versions, effect unverified).**
   - sab-air: `command -v pi` → `/opt/homebrew/bin/pi`, which is `pi 1.4.0` (`/opt/homebrew/lib/node_modules/@earendil-works/pi-coding-agent`).
   - sab-air: `~/.local/bin/pi` → `1.5.0` (managed, same as Mini).
   - `grok-pi-acp` runs `pi` by bare name (`--pi-bin` default `pi`, `grok-pi-acp.rs` `pi_bin` handling). So a PATH with `/opt/homebrew/bin` first would run 1.4.0.
   - Guess: this is the sab-air difference. Not confirmed by a run.
   - Fix: put `~/.local/bin` ahead of `/opt/homebrew/bin` in the PATH the pager sees, or set `PI_BIN` to the managed path.

3. **`cliproxy (none)` in the footer is not the failure cause (verified on Mini).**
   - The Mini footer shows `cliproxy (none)` while it answers `say hi` (capture above). So the text alone does not mean no model.
   - `(none)` is probably the thinking level or effort field: Mini `settings.json` sets `defaultThinkingLevel: high`, yet it shows `(none)`. Guess only.
   - Sab-air's cliproxy process and reachability were not confirmed in this scout (my probe output mixed local and remote process lists).
   - Next check: send `say hi` on sab-air and capture.

4. **Naming confusion (verified).** `pig`, `gb grok-pi`, `grok-pi` (`~/.local/bin/grok-pi`, Dwsy) and `grok-pi-acp` are four different things. Only `pig` and `gb` run the fork path. Fix: rename or document (`docs/HARNESS-FACTS.md` or the hub README).

## Follow-up context trace (item 3)

**Verdict:** the adapter does not resend history. Each prompt sends only the new message to Pi. Context lives in the one Pi process and its session.

- `crates/codegen/pi-grok-adapter/src/pi_adapter/agent.rs:308-309`: `json!({ "type": "prompt", "message": message })`. Images and `streamingBehavior` are added, but no prior turns.
- `agent.rs:1210-1213`: steering path sends `{"type":"prompt", "message", "streamingBehavior":"steer"}`, also message-only.
- `agent.rs:34-53`: `new_session` sends `{"type":"new_session"}` only when a session is created. A follow-up does not call it.
- `agent.rs:83-114`: `load_session` checks `requested != bootstrap.state.session_id` and rebinds. A context loss would appear here only if the ACP session id changed between turns.
- `crates/codegen/xai-grok-pager-bin/src/bin/grok-pi-acp.rs` (around line 470-500): one `PiRpc::spawn` per process, then `PiBootstrap::load`. The Pi child, and therefore its history, lives as long as the `grok-pi-acp` process.
- Pi's own session store (`~/.pi/agent/sessions/`) is read by Pi, not in this repo. Not read.

Evidence it works: Mini run 2 above, and the Mini `/resume` of the 1:30 PM session restored the prior turns in the chat.

Sab-air follow-up: the answer re-ran `Run Check agent-run-analysis contents`, `Run List files inside 2026-10-02 folder`, `Run List work subdirectory contents` before answering, so it did not answer from memory. Guess: the model chose to re-list. Not proven either way, because the first listing's top lines scrolled out of the capture.
