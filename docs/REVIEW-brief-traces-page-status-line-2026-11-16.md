# Spec review: Traces page status line (brief of 2026-11-16)

Reviewer: sonnet-5.5, read-only. Code read: `views/turn_status.rs`, `views/side_panel/mod.rs`, `views/traces_follow.rs`, `app/agent_view/{side_panel,render,session}.rs`, `acp/tracker.rs`, `app/agent.rs` (all under `crates/codegen/xai-grok-pager/src/`). Nothing was run; every line below is from reading code.

Verdict: the intent is clear and reachable. Four items below would make a builder pick wrongly or ship a row that disagrees with the stated states; none needs Sab, all are brief edits. Per delivery-policy, these are evidence, not a veto.

## Reachability (does the panel get the turn activity without a second source?)

Yes, but not from where the brief says.

- The brief says the row is "fed by `TurnActivity` from `acp/tracker.rs`". The chat does not feed it from the tracker directly. `render.rs:2609` calls `self.resolve_turn_activity()` (`session.rs:1306`), which wraps `session.turn_activity()` (`agent.rs:929`, tracker, only in `TurnRunning`) and adds the fallbacks: `Waiting(PromptAck)`, `Waiting(Subagent)`, and `Waiting(Model)` (`session.rs:1322-1336`), then `enrich_waiting_activity`. The tracker alone returns `None` in a plain model wait. State 2 (`Waiting for response…`, the exact case Sab quoted) exists only through `resolve_turn_activity`. A builder who reads the tracker would silently lose state 2.
- The per-activity timer is `AgentView.activity_started_at`, not tracker state. It is (re)armed at `render.rs:2617-2641` inside the chat's draw, only when `turn_status_height > 0`, and only on a phase transition of `resolve_turn_activity` against `last_activity`. The panel draws after the chat (`render.rs:988-1008`), so on a normal frame it can read the same field and show the same clock. That satisfies "no second clock", but only while the chat draw runs.
- The panel has no `AgentView`: `SidePanel::render(buf, area, info, theme, now_ms)` (`mod.rs:405`) gets an `Info` built per frame by `side_panel_info` (`app/agent_view/side_panel.rs:39`), and `draw_side_panel` (`:186`) is where it is built. The route is a new `Info` field (activity, `activity_started_at`, state, animation tick, plus whatever else `render_turn_status` needs; see 2) added in `side_panel_info`/`draw_side_panel`. `Ctx` (`mod.rs:92`) would need the same field to reach the Traces branch, or render reads `info` directly (it already does at `mod.rs:471`).
- The spinner needs `tick`, which the chat takes from `self.scrollback.animation_tick()` (`render.rs:2608`). The brief never says where the panel gets it; it must come through `Info` too, or the spinner freezes while the label and timer move.

## Findings

1. **The chat row hides the per-activity timer below 60 columns, so "reuse the status row's own formatting" contradicts "spinner, label, timer" at both required widths.** `render_turn_status` blanks `phase_timer_str` when `area.width < PHASE_TIMER_MIN_WIDTH` (`turn_status.rs:40`, `:431`; 60). The brief's snapshot widths are 43 and 21 (inner panel width, by the `filled_inner_width_43/21` convention in `side_panel/session.rs:312-328`; panel `MIN_WIDTH` 24 gives inner 21, `mod.rs:35`). Calling `render_turn_status` as-is gives no timer at 43 or 21, which fails states 2-4 and 5 ("the timer is never cut"). The brief must say one of: lower the threshold for the panel (a parameter, not a copy), or accept no timer under 60. The brief should also say that "columns" means inner width.

2. **Which parts of the chat row are "the same line" is undefined.** The chat row also draws a turn timer plus token count (`⇣Nk`), `[stop]`, `[↓]` hit areas, the interrupt hint (`· send a message to interrupt`), the queued-messages suffix, and the watcher cue (`turn_status.rs:270-560`). The brief names only spinner, label and per-activity timer. If the builder reuses `render_turn_status` whole, the panel gets a `[stop]` button with no hit-test and a turn timer, which the brief did not ask for; if it extracts the label/spinner/timer, the brief should say that and that `[stop]`, `[↓]`, `⇣Nk`, the turn timer, the interrupt hint and the queued suffix are not drawn. It also needs to say whether the mouse hit rects (`hit_cancel_button` etc., `render.rs:2729-2734`) stay untouched; a builder who passes the panel's output into them would overwrite the chat's rects.

3. **Non-turn rows the chat can show are not covered by "no turn in progress → no row" (state 1).** `should_show` (`turn_status.rs:773`) is also true for `parked` waits, a blocked drain, `Starting session…`, watchers still running with the agent idle, `CommandRunning` (worktree/fork), `Cancelling…`, `Verifying…` (goal mode), the plan-approval row (`render.rs:2650`), and the bash-turn `Running…`. The brief defines only "turn in progress" vs not. Decide, and write into the states: (a) is `Cancelling…` shown (it is a running-turn state with a label), (b) are the idle cues (parked, watcher, drain-blocked, starting) excluded, (c) the wake-turn display state (`wake_display_state`, `render.rs:1560`) and `send_now_gap` (`:1562`, activity forced to `None`) follow the chat or not. Without this a builder will guess three different ways, and the "one source" rule is only testable once the show/hide predicate is named.

4. **Collision with the follow view's own bottom status line (states 6, 8 and the height rule).** `Follow::render` (`traces_follow.rs:897-910`) already takes the last row of its area for `paused · N new · G live`, the agent filter, `note` and index errors, shrinking its body by one. The brief says "the last row above the page footer" and "takes one line from the follow view's height", but does not say which sits lower when both are present (state 6 has both: paused and running). It also leaves open `Follow::render` returning early when `area.height < 3` (`:898`), so with the panel taking one row the follow view hides at body heights 3 (currently drawn) and below; say what shows at tiny heights (status row first, or follow view first). State 8 has the same gap: the one-line note is drawn at `body.y` in `mod.rs:471-477` and returns early, so the status row has to be added in that branch and in the `Following` branch (`mod.rs:466-467`, also an early return) and the `Failed` branch; the brief should say all three, since a single insertion before the `match` is the obvious fix and is not what the code allows without restructuring.

5. **Zoomed and narrow-focused layouts and the stale timer (states 7, 9).** The panel can render while the chat draw is skipped: when the area is under `MIN_WIDTH + MIN_CHAT` (64) and the panel is focused, `split` gives the chat `width: 0` (`mod.rs:339-343`) and `draw_chat` does not run (`render.rs:988-1000`). Then `activity_started_at` and `last_activity` are not updated that frame; the row would show a label from the live tracker beside a timer anchored to a past phase (or none), the two-clocks mismatch the brief forbids. Zoom itself (`split`, `:347-350`) still leaves the chat `MIN_CHAT` (40) columns, so the chat draws and state 7 is fine. Needs either a rule (panel row hides when the chat did not draw) or a note that the builder must own the timer in that case. I could not verify whether `animation_tick` also stops without the chat draw; the builder should read it.

6. **State 4 is open ended.** "Whatever labels the chat row uses" is clear only if the builder reads `compute_activity` (`turn_status.rs:638-745`). Labels that exist: `Thinking…`, `Responding…`, `Compacting…`, `Retrying (attempt N)…`, `WritingToolCall` label, wait reasons (`reason.label()`), `Verifying…`, `Cancelling…`, `Running…`, `Waiting…`. State 5's "label truncates with `…`" also hides that a tool with no description renders `Run <highlighted command>` (syntax-highlighted via `tasks_pane::highlight_bash_command`), `Search <query>`, `Fetch <url>` or `Waiting on answers for …` (ask tools suppress the timer entirely, `turn_status.rs:421-431`), none of which are "the tool's description" (state 3). Say "as the chat shows it" for all, and decide whether the highlighted command is reused.

## Smaller points (nonblocking)

- State 9 asks for the same row focused and unfocused: with `focused` false the panel footer reads `F3 focus panel` (`mod.rs:445`). Say whether the status row sits between body and footer in both, and that the selection highlight (`draw_rows`, `mod.rs:~540`) is not applied to the row (the Traces branch draws via `Follow`, not `draw_rows`, so it is already outside it; say so).
- Redraw cadence: the 1 s `poll_side_panel` tick (`event_loop.rs:2747`) only marks the panel dirty; the spinner and the per-second timer need the same frame cadence the chat has during a turn. Probably free since the panel draws inside the chat's frame; the builder should confirm on screen at half width, not assume it.
- Both rows are on screen together while a turn runs: the chat's row and the panel's. Intended per Sab's words ("draw that same line as the last row of the Traces panel too").
- Theme: "colours from the fields the chat status row already uses" is right (`compute_activity` styles: `text_secondary`, `accent_success`, `warning`, `accent_error`, `gray`); AGENTS.md also requires looking at it in every shipped theme (`GROK_THEME`), which this brief's builder rules, run-no-cargo, do not cover. The lead's verification step needs it; the brief could point at it.
- The brief does not say how the panel row is tested at 43/21 given `SidePanel::render` needs an `Info`; the existing pattern is `snap(&Info, width)` in `side_panel/session.rs`. A Traces-page snapshot needs a `Following` state with a `Follow` (`traces_follow.rs` tests at `:1241-1260` build one). Naming those helpers saves a builder a guess.

## Contradictions with Sab's quoted words or grok-build behaviour

None found. The brief matches "draw that same line as the last row"; findings 1-3 are where "same line" is under-specified, not where it conflicts.
